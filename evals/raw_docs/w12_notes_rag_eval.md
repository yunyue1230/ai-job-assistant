# RAG 检索质量笔记：从切块到评测

写给自己的 checklist，每次改检索都过一遍。

## 一、切块

切块大小没有普适最优，但有几条经验：

- 500–1200 字（中文按字符，英文按 token 大约 200–400）是常见区间。太小会丢上下文，太大会稀释语义、让 embedding 变成一个「平均向量」，细节被抹平。
- 重叠 10%–20%。重叠太少，跨块的信息就断在边界上；重叠太多，同一段内容出现两次，检索会返回重复结果，浪费 top-k 名额。
- 按结构切比按长度切好：markdown 按标题层级、PDF 按段落、代码按函数。硬切会在句子中间断开，anchor 也对不上。
- 表格和列表是最容易切坏的。表格切一半，语义就反了。

我的做法是先按标题切，再对超长段做二次切分，切的时候优先在句号、分号处断开。

## 二、Embedding

选型看三件事：语言覆盖、维度与成本、领域匹配度。

- 中文场景优先看中文语料训练过的模型，纯英文模型在中文上会明显掉点；
- 维度影响存储和检索延迟，1024 维和 3072 维在召回上的差距往往小于「换个切块策略」带来的差距；
- 通用模型对代码、公式、专有名词不敏感，这类语料要么做查询改写，要么做微调。

一个反直觉的点：换 embedding 模型带来的 recall 提升，经常不如把切块和标注做对。所以改模型之前先把评测集建好。

## 三、向量索引

pgvector 支持两种索引，取舍不一样。

IVFFlat 是把向量聚成 lists 个簇，查询时只扫 probes 个最近的簇。建索引快、内存省，但需要数据先有一定量再建（空表建索引会导致簇划分很差），而且新插入的数据不在簇中心附近时召回会掉。lists 一般取行数除以 1000（小于 100 万行时）或开方，probes 从 1 往上调，调到召回可接受为止。

HNSW 是分层可导航小世界图，查询从上层稀疏图往下走，逐层细化。召回和延迟都比 IVFFlat 好，代价是建索引慢、内存占用高。关键参数：

- `m`：每个节点的最大连接数，默认 16。越大召回越好，内存越多。
- `ef_construction`：建索引时的候选队列长度，默认 64。越大图质量越好，建索引越慢。
- `ef_search`：查询时的候选队列长度，默认 40。可以在会话里临时调：`set local hnsw.ef_search = 100`。

生产上常见做法是建索引时给足 ef_construction，查询时按 SLO 调 ef_search。注意 HNSW 是近似索引，所以离线用精确余弦算出来的 recall 是上限，线上一定会掉一点，这个差值要单独监控。

另外，过滤条件和向量检索一起用时容易翻车：先过滤再检索会漏（候选集被切碎），先检索再过滤会不够数。pgvector 0.8 之后有 iterative scan，可以缓解「过滤后结果不足」的问题。

## 四、评测指标

- **Recall@k**：前 k 个结果里，命中的相关片段占全部相关片段的比例。适合「答案分散在多个块」的场景，比如跨块问题。
- **Precision@k**：前 k 个里有多少是相关的。上下文窗口有限时这个更重要。
- **MRR**：第一个相关结果排名的倒数的平均。只关心「第一个对的排多前」，适合问答类单片段场景。
- **nDCG@k**：考虑相关性等级（0/1/2/3）和位置折扣。有梯度标注时用它，比 recall 更细。
- **Hit Rate@k**：前 k 里有没有至少一个相关。最宽松，适合先看「有没有」。

指标要和服务目标对齐：问答产品关心「正确片段有没有进上下文」，所以 Recall@5 和 MRR 一起看；如果下游还要 rerank，那第一阶段的 Recall@50 更关键，MRR 意义不大。

## 五、标注的坑

- **别用 chunk id 做标签**。切块参数一变，id 指向的文本就变了，评测结果没法比较，而且不会报错，只会静默失真。
- 用**原文短引用**做标签，8–20 字、不跨标点，做空白折叠和小写化之后做子串匹配。匹配不到要报错，不能默认 0 分——静默的 0 分比崩溃更难查。
- 一条查询可以有多个相关块（跨块问题），标注时要都标上，否则 recall 天然上不去。
- 标注要包含「干扰项」：多份文档都提到同一个词，只有一份是正确来源。这类查询最能区分 embedding 模型的好坏，因为大家都能召回「提到这个词的块」，差别在排序。

## 六、混合检索与重排

纯向量检索对专有名词、型号、错误码不敏感（这些词的语义信息弱，靠字面反而准）。所以生产上常用混合检索：

- 一路 BM25 或全文索引（Postgres 的 tsvector、Elasticsearch）；
- 一路向量检索；
- 用 RRF 融合：`score = Σ 1/(k + rank_i)`，k 常取 60。RRF 只看排名不看分数，所以不需要归一化两路的分数量纲，这是它最大的好处。

重排（rerank）用 cross-encoder，把 query 和每个候选块拼起来送进模型打分。效果通常比向量召回好一截，代价是延迟随候选数线性增长，所以一般只对 top-20 到 top-50 做重排。

## 七、生成侧的坑

- 检索到的文本是**不可信输入**。文档里可能写着「忽略之前的指令」，必须当成数据而不是指令，system prompt 要明确这一点。
- 上下文拼装要带来源标识，方便做引用；引用做不出来，用户就没法验证。
- 上下文塞太满会掉效果（lost in the middle），把最相关的放开头和结尾，中间放次要的。
- 拒答要有明确策略：检索分数低于阈值时直接说「没找到」，比编一个答案好。

## 八、成本

一次 live 评测的成本 = 语料块数 + 查询数 的 embedding 调用。300 块语料 + 30 条查询，按批量 10 条一批，大概 33 次请求，成本几毛钱。所以「先跑一次 live，之后所有指标改动都离线复算」是标准做法：把预测快照存下来，指标只是快照的纯函数。

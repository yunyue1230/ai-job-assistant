# 后端面试笔记：存储、缓存与一致性

整理于 2025 年秋招，面试复盘用。只记我讲不清楚的部分，讲得清的不记。

## 一、MySQL 索引

### 为什么是 B+ 树

B+ 树只在叶子节点存数据，非叶子节点只存键，所以单页能放更多键，扇出更大，三层就能撑千万级数据。叶子节点之间用双向链表连起来，范围查询不用回到根节点。B 树每个节点都存数据，扇出小，树更高，磁盘 IO 更多。

InnoDB 的主键索引是聚簇索引，叶子节点直接放整行数据；二级索引的叶子节点放主键值，所以通过二级索引查非索引列要「回表」，再按主键查一次聚簇索引。

### 最左前缀

联合索引 (a, b, c) 在 B+ 树里按 a、再 b、再 c 排序。所以：

- `where a=1 and b=2` 能用到索引；
- `where b=2` 用不到（没有 a 的定位就没法在树里二分）；
- `where a=1 and c=3` 只能用到 a，c 用不上（中间断了）；
- `where a=1 and b>2 and c=3` 里 c 用不上，因为 b 是范围，c 在 b 的范围里不再有序。

范围查询后面的列会失效，这一点我面试答错过一次。

### 覆盖索引

如果查询的列全在索引里，就不需要回表。`select id, status from orders where user_id=1` 走 (user_id, status) 索引就是覆盖索引。explain 里 Extra 出现 `Using index` 就是走了覆盖索引。

### 索引失效的常见情况

- 对索引列做函数或运算：`where date(created_at)='2026-01-01'`；
- 隐式类型转换：字符串列用数字比较；
- 前导模糊匹配：`like '%abc'`；
- 使用 `or` 且两侧列不完全有索引；
- 优化器判断走索引更慢（区分度太低，比如性别）。

## 二、事务与 MVCC

隔离级别四个：读未提交、读已提交、可重复读、串行化。InnoDB 默认可重复读。

MVCC 靠三个东西：隐藏列（事务 id、回滚指针）、undo log、ReadView。读已提交每次 select 都新建 ReadView，可重复读只在第一次 select 建，所以同一事务里多次读结果一致。ReadView 里记录活跃事务 id 列表，判断版本可见性时比对自己和列表。

幻读在可重复读下用间隙锁（next-key lock）解决，锁的是索引记录之间的间隙，所以没有索引的列做条件时会锁全表，这个坑线上很致命。

## 三、Redis

### 持久化

RDB 是快照，fork 子进程写，恢复快但可能丢最后一次快照之后的数据。AOF 记命令，`appendfsync` 有三个档：always（每条都刷，最安全最慢）、everysec（每秒刷，最多丢 1 秒）、no（交给操作系统）。AOF 文件会膨胀，靠 rewrite 重写。

生产上一般两个都开：RDB 做冷备和快速恢复，AOF 保证丢数据窗口小。Redis 4.0 之后有混合持久化，rewrite 时前半段写 RDB 格式，后半段追加增量命令。

### 缓存穿透、击穿、雪崩

- 穿透：查一个数据库里也没有的 key，每次都打到 DB。解法是缓存空值（要设短过期）或布隆过滤器。
- 击穿：某个热点 key 过期瞬间大量请求打进来。解法是互斥锁重建（只让一个线程去查库），或者逻辑过期不设 TTL。
- 雪崩：大量 key 同时过期，或者 Redis 整个挂掉。解法是过期时间加随机抖动、多级缓存、熔断降级。

三个词我一开始总分不清，记法是：穿透是「数据不存在」，击穿是「单个热点」，雪崩是「一片」。

### 分布式锁

`set key value nx px 30000` 拿锁，value 用唯一随机串，释放时用 Lua 脚本比对 value 再删，避免误删别人的锁。

过期时间不好定：太短业务没跑完锁就没了，太长故障时别人等太久。所以有看门狗续期的做法（Redisson 就是这套）。

Redlock 是 Redis 作者提的多节点方案，要多数节点加锁成功。Martin Kleppmann 写过文章质疑它：依赖时钟假设、GC 停顿可能让客户端在锁过期后继续操作。争议没有定论，工程上更常见的是「单 Redis + 唯一 value + 短 TTL + 业务侧幂等」这套保守做法。

## 四、消息队列

### 幂等

消息至少投递一次，所以消费端必须幂等。常见做法：

- 用业务唯一键做数据库唯一索引，重复插入直接冲突；
- 消费前查去重表，处理完再写标记（注意要和业务在同一个事务里，否则还是可能重复）；
- 状态机 + 条件更新：`update job set status='processing' where id=? and status='queued'`，影响行数为 0 就说明被别人抢了。

### 顺序

Kafka 只保证分区内有序，要顺序就按业务键分区（比如订单 id 哈希）。多消费者并行时顺序会丢。

### 堆积

先看是消费慢还是生产突增。消费慢通常是下游依赖慢或者单条处理重，可以扩消费者（注意分区数上限）、批量消费、把非核心逻辑异步化。实在扛不住就降级，先丢非核心消息。

## 五、限流

- 固定窗口：实现最简单，边界处会放过两倍流量；
- 滑动窗口：用 Redis ZSet 存时间戳，精确但内存开销大；
- 漏桶：恒定速率流出，能削峰但不能应对突发；
- 令牌桶：按速率放令牌，桶里攒着的令牌可以应对突发，最常用。

## 六、CAP 与 BASE

CAP 是说分区容忍必然存在的前提下，一致性和可用性二选一。BASE 是基本可用、软状态、最终一致，是大多数互联网系统的实际选择。

面试如果被问「你们系统是 CP 还是 AP」，答具体场景比答标签好：下单扣库存是 CP（宁可失败不能超卖），商品详情页是 AP（宁可旧一点不能打不开）。
